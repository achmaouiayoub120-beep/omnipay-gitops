# ADR-007 — Stratégie de déploiement progressif Canary avec Argo Rollouts

## Statut
**Accepté**

## Porteur
**P4 — Ingénieur DevSecOps (Livraison & Chaîne d'Approvisionnement)**

## Contexte
Le microservice `transaction-service` est le cœur transactionnel de la néobanque OmniPay. Tout dysfonctionnement en production (régression logique, fuite mémoire, surcharge ou erreurs 5xx) entraîne des pertes financières directes et une dégradation immédiate du Service Level Objective (SLO de disponibilité fixé à 99.9%).

Les déploiements traditionnels de Kubernetes (`Deployment` avec stratégie `RollingUpdate`) présentent des lacunes majeures :
1. Ils n'analysent pas les métriques de santé applicative réelle (latence, taux d'erreur HTTP 5xx) : ils considèrent qu'un pod est sain dès lors que sa sonde HTTP `readinessProbe` renvoie 200.
2. Si une nouvelle version échoue sous trafic réel, le RollingUpdate continue de remplacer les anciens pods jusqu'à ce que 100% du trafic soit servi par la version buggée.
3. Le retour arrière (rollback) nécessite l'intervention d'un ingénieur d'astreinte, augmentant le MTTR (Mean Time To Recovery).

## Décision
Nous remplaçons l'objet Kubernetes `Deployment` par un objet **`Rollout` (Argo Rollouts)** pour `transaction-service` dans l'environnement de production (`omnipay-prod`).

Nous configurons une stratégie **Canary progressive pilotée par les métriques Prometheus** :
- **Paliers de déploiement progressifs** :
  1. Palier 1 : **10%** du trafic routé vers la nouvelle version (Canary), pause de 30 secondes pour observation.
  2. Évaluation métrique automatique : Exécution d'un `AnalysisTemplate` (`prometheus-error-rate-5xx`).
  3. Palier 2 : **50%** du trafic routé vers le Canary, pause de 30 secondes pour observation sous charge accrue.
  4. Deuxième évaluation métrique automatique.
  5. Palier 3 : Promotion finale à **100%** si tous les contrôles sont au vert.
- **Critère de succès automatisé (SLO Guardrail)** :
  - Métrique interrogée : Taux de réponses HTTP 5xx calculé par Prometheus (`http://monitoring-kube-prometheus-prometheus.monitoring.svc:9090`).
  - Condition de validation : `result[0] < 2.0` (taux d'erreur strictement inférieur à 2%).
  - En cas de dépassement (`failureLimit: 1`) : Le contrôleur Argo Rollouts avorte immédiatement la mise en production (`Degraded`), isole la version défectueuse et redirige 100% du trafic client sur la version stable précédente en moins de 10 secondes.

## Alternatives étudiées
1. **Kubernetes Deployment standard (RollingUpdate)** :
   - *Inconvénients* : Aveugle aux métriques métier, aucun rollback automatique basé sur le taux d'erreur réel, risque d'impacter 100% des clients bancaires.
2. **Blue/Green Deployment basique** :
   - *Avantages* : Rollback rapide en cas de problème franc.
   - *Inconvénients* : Bascule instantanée de 100% du trafic sans phase de test sur un échantillon d'utilisateurs réels (blast radius maximal). Doublement de l'empreinte mémoire nécessaire sur K3s.
3. **Flagger (Weaveworks)** :
   - *Avantages* : Bon outil de déploiement progressif.
   - *Inconvénients* : Dépendance forte envers un Service Mesh complet (Istio ou Linkerd), complexité d'exploitation supérieure pour notre architecture K3s légère sans apporter d'avantage déterminant par rapport à Argo Rollouts.

## Conséquences
- **Positives** :
  - Limitation du rayon d'impact (Blast Radius) à 10% maximum des utilisateurs lors d'une anomalie.
  - Rollback instantané sans intervention humaine (MTTR quasi-nul).
  - Validation continue des SLOs au moment même de la livraison logicielle.
  - Visualisation claire via le dashboard Argo Rollouts et les alertes Prometheus.
- **Négatives / Défis** :
  - Nécessite la présence des services Kubernetes distincts (`transaction-service-active` et `transaction-service-preview`).
  - Dépendance envers la disponibilité du serveur Prometheus interne pour l'évaluation des métriques.

## Sécurité et Résilience
- La stratégie Canary protège les transactions financières contre les régressions non détectées par les tests unitaires ou d'intégration.
- Si le serveur Prometheus est temporairement injoignable, Argo Rollouts se met en état d'alerte et bloque la promotion automatique plutôt que d'autoriser une version non vérifiée (principe Zero-Trust : "Fail-Safe Defaults").

## Justification
Argo Rollouts offre le plus haut degré de maturité et d'automatisation pour les opérations SRE critiques. Il garantit la résilience opérationnelle exigée pour les flux financiers d'OmniPay.
