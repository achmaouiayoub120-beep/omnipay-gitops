# ADR-013 : Tracing distribué unifié (Tempo / OpenTelemetry) et corrélation Traces-Metrics-Logs pour la gouvernance SRE

- **Statut** : **Accepté**
- **Date** : Semaine 3 (S3) — 2026-11-22
- **Porteur** : P5 — Moad Helkamel (Ingénieur SRE, Fiabilité & Observabilité)
- **Parties prenantes consultées** : P2 (Architecture Backend & Microservices), P3 (CI/CD Pipeline), P4 (Packaging, GitOps & Kubernetes)
- **Environnements impactés** : `platform/monitoring`, `omnipay-dev`, `omnipay-recette`, `omnipay-prod`

---

## 1. Contexte & Problématique

Dans l'architecture bancaire distribuée de la néobanque **OmniPay Zero-Trust**, une transaction bancaire (ex: virement de fonds via `/api/transactions/transfer`) traverse une chaîne complexe de microservices et de dépendances :

1. **Ingress NGINX Controller** (point d'entrée réseau, terminaison TLS et filtrage WAF) ;
2. **Auth Service (port 8081)** (authentification JWT, validation des autorisations RBAC Zero-Trust) ;
3. **Transaction Service (port 8082)** (règles métier bancaires, contrôle de solde, transactions ACID) ;
4. **PostgreSQL Database** (persistance des comptes et écritures comptables) ;
5. **Notification Service (port 8083)** (émission d'accusés de réception et alertes client).

### Limites des piliers isolés (Métriques et Logs) :
- **Prometheus** alerte efficacement sur un dépassement du SLO de latence (ex: P95 > 200ms) ou une hausse du taux d'erreurs HTTP 5xx. Cependant, les métriques agrégées sont incapables d'identifier *quel appel précis* au sein d'une chaîne de dépendances est responsable du ralentissement.
- **Loki** centralise les journaux applicatifs. Cependant, sous fort volume de transactions concurrentes, retrouver la séquence exacte des logs liés à une requête cliente nécessite un identifiant de corrélation universel et une navigation sans friction.

Sans **Tracing Distribué de bout en bout**, l'équipe SRE et les développeurs subissent un **Mean Time to Detect (TTD)** et un **Mean Time to Resolve (MTTR)** excessifs, compromettant le budget d'erreur mensuel alloué (SLO 99.5%).

---

## 2. Facteurs de Décision (Decision Drivers)

1. **Complétude de la Triade d'Observabilité 360°** : Unifier nativement **Métriques (Prometheus) ↔ Logs (Loki) ↔ Traces (Tempo)** au sein d'une interface unique (Grafana).
2. **Contraintes strictes de ressources K3s** : Le composant de traçage doit fonctionner sur un cluster local ou VM étudiante avec une empreinte mémoire restreinte (**< 256Mi RAM**).
3. **Standard ouvert de l'industrie (OpenTelemetry)** : Adoption de la spécification **W3C Trace Context (`traceparent`)** évitant tout verrouillage propriétaire et supportée nativement par Spring Boot 3.4 et Micrometer Tracing.
4. **Zero-Index & Efficacité Stockage** : Pas de base de données NoSQL lourde (Elasticsearch ou Cassandra) nécessitant plusieurs gigaoctets de mémoire pour indexer les traces.
5. **Simplicité d'Exploitation GitOps** : Déploiement reproductible via Helm, manifestes versionnés et intégration dans le socle existant `kube-prometheus-stack`.

---

## 3. Options Étudiées et Comparaison

| Critère d'évaluation | Option 1 : Grafana Tempo (Retenue) | Option 2 : Jaeger avec Elasticsearch / Cassandra | Option 3 : OpenZipkin |
|---|---|---|---|
| **Consommation Mémoire (RAM)** | **128Mi - 256Mi (Mode Standalone)** | 2.5Go - 4Go (Elasticsearch / JVM) | ~512Mi - 1Go |
| **Indexation & Stockage** | **Zero-index (Stockage objet / local-path 5Gi)** | Indexation inversée lourde | MySQL ou Cassandra |
| **Corrélation Grafana** | **Native (tracesToLogsV2, tracesToMetrics, NodeGraph)** | Partielle via plugin tiers | Limitée |
| **Support OpenTelemetry OTLP** | **Natif (gRPC :4317, HTTP :4318)** | Via agent/collecteur dédié | Partiel |
| **Compatibilité K3s compact** | **Excellente** | Incompatible (OOM cluster) | Moyenne |

---

## 4. Décision d'Architecture

L'équipe SRE retient formellement **Grafana Tempo (Option 1)** en mode **Standalone** (monolithique compact) sur le cluster K3s dans le namespace `monitoring`.

### Modalités techniques de mise en œuvre :
1. **Déploiement Helm & Allocation de Ressources** :
   - Chart Helm : `grafana/tempo` version `1.10.3`.
   - Ressources K8s : `requests: { memory: "128Mi", cpu: "100m" }`, `limits: { memory: "256Mi", cpu: "250m" }`.
   - Persistance : Volume local K3s `local-path` de `5Gi` avec une rétention paramétrée à `24h`.
2. **Protocoles et Récepteurs activés** :
   - **OTLP gRPC (port 4317)** et **OTLP HTTP (port 4318)** exposés en interne (`tempo.monitoring.svc.cluster.local`).
   - Récepteur Jaeger Thrift (port 14268) activé pour compatibilité legacy.
3. **Spécification pour les microservices Spring Boot (Rôle P2)** :
   - Utilisation de `micrometer-tracing-bridge-otel` et `opentelemetry-exporter-otlp`.
   - Échantillonnage à 100% en dev/recette et 10% en production.
   - Propagation stricte des en-têtes W3C `traceparent`.
4. **Provisioning de la Datasource Grafana (`datasource-tempo.yaml`)** :
   - Configuration de **`tracesToLogsV2`** vers la datasource Loki : un clic sur une span de trace déclenche la requête LogQL `{namespace="default", app="${__span.tags["service.name"]}"} |= "${__trace.id}"`.
   - Configuration de **`tracesToMetrics`** vers Prometheus pour basculer d'une span vers les métriques RED (RPS et latence P95).
   - Activation du **ServiceMap & NodeGraph** pour la visualisation topologique des flux inter-services.

## 5. Conséquences

### Conséquences Positives :
- **Diagnostic instantané des pannes (MTTR divisé par 3)** : Lorsqu'une alerte Multi-Burn-Rate retentit sur Discord, l'ingénieur SRE isole le goulot d'étranglement exact (ex: verrou SQL Postgres ou latence JWT Auth) en moins de 30 secondes.
- **Corrélation 360° sans friction** : Passerelle fluide Métriques ➔ Traces ➔ Logs sans recopie manuelle d'identifiant.
- **Empreinte minimale** : Tempo consomme moins de 200Mi de RAM en régime de croisière sur K3s.
- **Conformité Audit Bancaire** : Traçabilité des flux financiers respectant le principe Zero-Trust (aucun numéro de carte ou secret n'est propagé dans les tags de span).

### Conséquences Négatives & Mesures d'Atténuation :
- *Rétention courte (24h)* : En mode standalone sur disque local, la rétention est limitée à 24 heures pour préserver l'espace disque du nœud K3s.  
  *Mitigation* : Les métriques agrégées sont conservées 7 jours dans Prometheus et les logs d'erreurs 7 jours dans Loki.
- *Recherche de traces non indexées* : La recherche directe par attribut textuel dans Tempo peut être plus lente qu'avec Elasticsearch.  
  *Mitigation* : Utilisation conjointe de Grafana Explore qui utilise Loki pour retrouver le `traceId` à partir des logs, puis interroge Tempo par identifiant direct.
