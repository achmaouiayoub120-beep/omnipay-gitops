# ADR-005 — Sécurisation de la supply chain logicielle : SBOM Syft, Cosign & Kyverno

## Statut
**Accepté**

## Porteur
**P4 — Ingénieur DevSecOps (Livraison & Chaîne d'Approvisionnement)**

## Contexte
Les attaques ciblant la chaîne d'approvisionnement logicielle (Software Supply Chain Attacks, telles que SolarWinds, Codecov ou la compromission de paquets malveillants npm/Maven) démontrent qu'il ne suffit plus de protéger l'infrastructure runtime : il est impératif de garantir l'authenticité et l'intégrité de chaque paquet logiciel depuis la ligne de code jusqu'au pod en cours d'exécution.

Pour une plateforme financière Zero-Trust comme OmniPay, nous devons répondre à trois questions fondamentales :
1. *De quoi est composé exactement chaque conteneur déployé ?* (Transparence des dépendances).
2. *L'image provient-elle bien de notre pipeline officiel et est-elle exempte d'altération ?* (Authenticité cryptographique).
3. *Le cluster Kubernetes peut-il refuser catégoriquement toute image inconnue, modifiée ou non signée ?* (Admission Control Zero-Trust).

## Décision
Nous concevons et déployons une **chaîne de confiance logicielle cryptographique bout en bout** reposant sur le triptyque :
1. **Génération de SBOM avec Syft (Anchore)** : Génération systématique du Software Bill of Materials au format standardisé SPDX (`sbom.spdx.json`) lors du build Jenkins.
2. **Signature cryptographique avec Cosign (Sigstore)** : Signature sans dépendance complexe des images OCI dans Harbor avec une paire de clés ECDSA P-256. Le SBOM généré est attaché directement à l'image dans le registre OCI (`cosign attach sbom`).
3. **Contrôle d'admission strict avec Kyverno** : Déploiement d'une `ClusterPolicy` (`verify-omnipay-image-signature`) avec `validationFailureAction: Enforce`. Kyverno intercepte chaque tentative de création de pod dans `omnipay-prod` et `omnipay-recette` et vérifie mathématiquement la signature Cosign avec la clé publique autorisée. Toute image non signée est rejetée avec un code d'erreur 403 Forbidden.

## Alternatives étudiées
1. **Docker Content Trust / Notary v1** :
   - *Inconvénients* : Nécessite un serveur de métadonnées Notary séparé lourd à maintenir, protocole obsolète non aligné avec les standards OCI Artifacts v1.1, manque de souplesse pour les politiques d'admission K8s modernes.
2. **Open Policy Agent (OPA) / Gatekeeper avec Ratify** :
   - *Avantages* : Très puissant et flexible avec le langage Rego.
   - *Inconvénients* : Courbe d'apprentissage élevée du langage Rego pour toute l'équipe, verbosité des politiques, intégration de vérification de signature plus complexe à configurer que la directive native `verifyImages` de Kyverno.
3. **Absence de contrôle d'admission (Confiance implicite dans le registre)** :
   - *Rejeté catégoriquement* : Viole le principe de base du Zero-Trust ("Never Trust, Always Verify"). Un attaquant parvenant à injecter une image malveillante dans le cluster ou le registre verrait son pod exécuté sans barrière.

## Conséquences
- **Positives** :
  - Impossibilité pour un tiers ou un pirate de déployer une image conteneur non approuvée dans les environnements sensibles.
  - Inventaire exhaustif des dépendances logicielles (SBOM) prêt pour l'analyse des vulnérabilités Zero-Day.
  - Politiques Kubernetes déclaratives et lisibles en YAML natif (Kyverno).
- **Négatives / Défis** :
  - Obligation d'automatiser rigoureusement l'étape de signature dans Jenkins : si la clé expire ou est mal configurée, les déploiements sont bloqués.
  - Gestion sécurisée de la clé privée `cosign.key` (stockée dans les credentials protégés de Jenkins).

## Sécurité
- La clé privée `cosign.key` est chiffrée par mot de passe et n'est jamais committée dans Git.
- Seule la clé publique `cosign.pub` est versionnée et intégrée dans la politique d'admission Kyverno.
- La politique s'exécute en mode synchrone (`validationFailureAction: Enforce`), bloquant la requête au niveau de l'API Server avant toute exécution de conteneur.

## Justification
Cette chaîne de confiance concrétise les plus hautes exigences des référentiels NIST SSDF (Secure Software Development Framework), CISA et de la directive européenne NIS 2 en matière d'intégrité de la chaîne d'approvisionnement logicielle.
