# ADR-004 — Choix du modèle de déploiement continu GitOps avec ArgoCD

## Statut
**Accepté**

## Porteur
**P4 — Ingénieur DevSecOps (Livraison & Chaîne d'Approvisionnement)**

## Contexte
La livraison continue (CD) vers le cluster Kubernetes doit respecter des impératifs rigoureux de gouvernance bancaire :
1. **Élimination des secrets d'infrastructure dans la CI** : Le moteur Jenkins (P1) ne doit détenir aucun jeton `cluster-admin` ni certificat kubeconfig autorisant l'accès direct aux nœuds K3s.
2. **Auditabilité et traçabilité absolue (Single Source of Truth)** : Toute modification de configuration ou version applicative doit être tracée par un commit Git immuable.
3. **Prévention et correction des dérives (Anti-Drift / Self-Healing)** : Si un administrateur ou un attaquant modifie un objet Kubernetes directement via `kubectl`, le système doit rétablir l'état désiré en continu.
4. **Gestion multi-environnements scalable** : Déployer et maintenir de manière cohérente 3 environnements cibles (`dev`, `recette`, `prod`).

## Décision
Nous adoptons le modèle **GitOps "Pull"** piloté par **ArgoCD**, orchestré à l'aide d'un **ApplicationSet** unique pour gérer les trois environnements (`dev`, `recette`, `prod`).

Principes d'implémentation :
- **Dépôt d'état désiré dédié** : `https://github.com/achmaouiayoub120-beep/omnipay-gitops.git`.
- **ApplicationSet `omnipay-environments`** : Utilisation d'un générateur `list` instanciant automatiquement les applications `omnipay-dev`, `omnipay-recette`, et `omnipay-prod`.
- **Politique de réconciliation automatique** : `prune: true` et `selfHeal: true` pour dev et recette; politique mesurée pour la production.
- **Rôle de Jenkins limité à Git** : À l'issue d'un build réussi, Jenkins se contente de committer le nouveau tag d'image dans `envs/dev/kustomization.yaml`. ArgoCD détecte l'écart et l'applique au cluster.

## Alternatives étudiées
1. **Déploiement direct "Push" depuis Jenkins (`kubectl apply / helm upgrade`)** :
   - *Inconvénients critiques* : Nécessite de confier un kubeconfig administrateur au runner Jenkins. En cas de vulnérabilité ou compromission de l'agent CI, l'ensemble du cluster K3s tombe aux mains de l'attaquant. Modèle catégoriquement rejeté en architecture Zero-Trust.
2. **Flux v2 (GitOps)** :
   - *Avantages* : Très modulaire et léger.
   - *Inconvénients* : Interface graphique web moins avancée pour le suivi visuel en temps réel lors des soutenances et revues d'architecture. Gestion des ApplicationSets moins intégrée.
3. **Déploiement manuel via scripts shell exécutés par les opérateurs** :
   - *Rejeté* : Risque d'erreur humaine majeur, dérive de configuration inévitable, absence totale de traçabilité Git.

## Conséquences
- **Positives** :
  - Séparation étanche des responsabilités : Jenkins construit les artefacts, ArgoCD les déploie.
  - Détection immédiate du drift et restauration automatique de l'état désiré.
  - Rollback instantané : un simple `git revert` suffit à revenir à l'état antérieur sain.
  - Visibilité claire des statuts de synchronisation et de santé des pods.
- **Négatives / Défis** :
  - Léger délai de réconciliation (polling Git périodique, configurable à 60s ou webhook).
  - Nécessité de maîtriser la syntaxe des manifests Kustomize et des CRDs ArgoCD.

## Sécurité
- ArgoCD s'exécute dans son propre namespace isolé (`argocd`).
- Seul le contrôleur ArgoCD possède les droits d'écriture sur les namespaces cibles (`omnipay-*`).
- Les politiques RBAC d'ArgoCD interdisent les modifications non autorisées par l'interface web.

## Justification
Le modèle GitOps incarné par ArgoCD concrétise l'axiome fondamental du Zero-Trust : "Zéro privilège d'administration partagé entre la CI et la Production".
