# ADR-002 — Choix du registre d'images privé sécurisé Harbor

## Statut
**Accepté**

## Porteur
**P4 — Ingénieur DevSecOps (Livraison & Chaîne d'Approvisionnement)**

## Contexte
Dans le cadre de l'architecture bancaire Zero-Trust d'OmniPay, les artefacts logiciels conteneurisés (microservices `auth-service`, `transaction-service`, `notification-service`) constituent des composants sensibles contenant la logique métier financière.

Les exigences de sécurité et de conformité imposent :
1. **Souveraineté et isolation des données** : Les images doivent être hébergées sur notre infrastructure dédiée (K3s on-premise) sans dépendre d'un registre public exposé sur Internet.
2. **Analyse de vulnérabilités Shift-Left intégrée** : Chaque image poussée dans le registre doit être scannée automatiquement avant d'être éligible à un déploiement.
3. **Moindre privilège et traçabilité** : L'accès en écriture (CI) et en lecture (Kubernetes) doit être strictement cloisonné par des comptes robots éphémères ou nominatifs.
4. **Support des spécifications OCI modernes** : Capacité de stocker non seulement des images conteneurs, mais également des métadonnées cryptographiques (signatures Cosign, attestations et SBOM SPDX).

## Décision
Nous retenons **Harbor Enterprise Private Registry** (projet CNCF Graduated) déployé via son Helm Chart officiel sur le cluster K3s dans le namespace `harbor`, exposé sur le port NodePort `30002` (`http://harbor.omnipay.local:30002`).

Les choix de configuration clés sont :
- **Moteur d'analyse Trivy activé** : Scan automatique déclenché à chaque push d'image (`auto_scan: true`).
- **Projet dédié `omnipay`** : Cloisonnement strict des artefacts du projet.
- **Authentification par Robot Account** : Création du compte de service `robot$robot-omnipay-ci` disposant uniquement des privilèges requis pour pousser les images et artefacts OCI depuis Jenkins.
- **Stockage et cache OCI** : Persistance adaptée aux disques locaux du cluster K3s.

## Alternatives étudiées
1. **Docker Hub (SaaS Public)** :
   - *Inconvénients* : Quotas de débit stricts (rate limiting), risque de fuite de code sensible en cas de mauvaise configuration de visibilité, dépendance envers une connexion internet externe permanente. Rejeté pour non-conformité Zero-Trust.
2. **Docker Registry v2 standard (registry:2)** :
   - *Avantages* : Empreinte mémoire minime (~50 Mo).
   - *Inconvénients* : Aucun scanner de vulnérabilité intégré, absence totale d'interface graphique et de gestion RBAC fine des droits d'accès par projet. Rejeté pour absence de fonctions de sécurité.
3. **Quay Enterprise (Red Hat)** :
   - *Avantages* : Sécurité avancée, Clair intégré.
   - *Inconvénients* : Empreinte mémoire et complexité d'installation démesurées pour un cluster K3s léger.

## Conséquences
- **Positives** :
  - Détection précoce des vulnérabilités (CVE) dans les couches de base et les paquets OS.
  - Conformité totale avec le modèle Zero-Trust : le registre n'autorise aucun accès anonyme.
  - Compatibilité parfaite avec Cosign et Syft grâce au support OCI Registry v1.1.
- **Négatives / Défis** :
  - Consommation mémoire d'environ 1.5 Go de RAM sur le cluster K3s.
  - Nécessité d'initialiser les credentials robot via script d'automatisation lors du bootstrap initial.

## Sécurité
- Les secrets du compte robot Harbor sont automatiquement propagés dans les namespaces applicatifs (`omnipay-dev`, `omnipay-recette`, `omnipay-prod`) sous la forme de `docker-registry` Secrets Kubernetes (`harbor-registry-secret`).
- Tout accès interactif administrateur utilise un mot de passe renforcé stocké de façon étanche.

## Justification
Harbor est la référence industrielle open source pour la gouvernance des conteneurs. Son intégration native avec Trivy et le standard OCI en fait le pilier incontournable de la chaîne d'approvisionnement sécurisée d'OmniPay.
